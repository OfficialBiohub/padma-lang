# M9 Application Platform Architecture

**Status:** Design contract before implementation

Padma M9 expands practical application support without turning the interpreter into an unrestricted server host, package installer, credential vault, or browser controller. Every component remains opt-in through a manifest capability and retains a Termux-first local workflow.

## Delivery sequence

| Increment | Stable first scope | Explicitly deferred |
|---|---|---|
| Web | Local-only HTTP server, fixed loopback binding, literal routes, bounded JSON body/response, `server:local` grant | Public listen addresses, TLS termination, arbitrary middleware |
| Database | Project-root SQLite file, named migrations, parameter-bound values, typed JSON rows, `database:sqlite` grant | Raw SQL evaluation from Padma source, remote database URLs, ORM code generation |
| Packages | Signed index metadata, content hash, immutable lock entries, project-local package root | Unreviewed global installs, lifecycle scripts, arbitrary Git execution |
| Identity | Password hash adapter, signed expiring session records, secure-cookie response builder, environment-named secrets | OAuth provider defaults, password recovery delivery, public auth hosting |
| Deployment | Manifest validator and dry-run plan; explicit confirmation before remote action | Automatic publishing, embedded deployment credentials |
| GUI/mobile | Declarative JSON UI adapter and a Termux renderer example | Automatic Android permission elevation, hidden background service |
| AI | Structured provider-neutral workflow helpers and local-adapter bridge | Model training engine, automatic execution of model output |
| Browser | Domain-allowlisted inspect/navigation plan with redaction and side-effect confirmation | Login/CAPTCHA bypass, payment/posting without user confirmation |

## Security rules

Database values must always use parameter binding. OWASP describes prepared statements as separating fixed SQL code from data and preventing supplied values from changing query intent; SQLite’s own statement lifecycle is prepare, bind, step, reset, and finalize.[1] [2]

The initial Termux adapter invokes the installed `sqlite3` CLI only with a project-root database file and a fixed, internal statement set. It sends `.parameter` bindings before each fixed statement, requests `.mode json` only for record reads, turns `.bail on`, and sets the CLI lock wait with `.timeout 5000`; user-provided database values are hex-encoded for the binding channel rather than interpolated into SQL text.[5]

Padma’s first atomic write interface is a non-nestable fixed `db.apply(database, operations)` batch, not a callback-based transaction or SQL console. It emits exactly one `BEGIN IMMEDIATE` / `COMMIT` sequence for a single database, so write-lock contention is detected before any batch operation begins. SQLite documents that `BEGIN...COMMIT` transactions do not nest, permits only one simultaneous write transaction, and rolls back an unfinished transaction when the connection closes; a failed bounded CLI invocation therefore never reports success to the caller.[6]

Session identifiers must be generated by a cryptographically secure generator, remain meaningless to clients, expire, and be stored server-side. OWASP recommends at least 64 bits of entropy and describes 128 bits as a suitable target for custom session IDs.[3]

Package resolution produces a committed lock file containing exact selected versions and integrity hashes. This follows the reproducibility objective of lock files: later installs use the same dependency tree despite intermediate registry changes.[4]

The first registry increment is deliberately local-only. A package is a directory under the project’s `packages/` root with a versioned `padma-package.toml` manifest and a digest of a canonical file listing; it has no `install`, `preinstall`, `postinstall`, shell, Git, archive-extraction, or lifecycle hook field. `padma package lock` resolves only direct manifest-declared local paths, writes canonical sorted JSON to `padma.lock`, and records the package’s logical name, exact version, project-relative resolved path, declared exports, requested capability set, and SHA-256 digest. Npm documents the reproducibility role of committed lockfiles and records package location, resolved origin, integrity, and install-script presence; Padma retains the reproducibility and integrity elements while refusing installation scripts entirely.[7]

`padma package verify` re-hashes already-present package directories and compares them with the lockfile. It never downloads, unpacks, or executes a package. This all-or-nothing, locally recorded digest policy follows the useful integrity property of hash-checking workflows: each resolved dependency must be pinned and hashed rather than mixing protected and unprotected dependency entries.[8] Registry publishing, remote fetch, and package signature verification remain deferred until Padma has a reviewed root-key and index-rotation policy; Cargo’s registry index illustrates why package-name restrictions, version uniqueness, versioned index schemas, and per-package SHA-256 checksums should be explicit rather than implicit.[9]

No M9 component silently opens a public port, uses a secret literal from Padma source, launches a background daemon, installs an unverified package, or performs browser side effects. Each external action is capability-gated and surfaces a localized diagnostic.

## Termux operation boundary

`padma serve` is for local development on the phone. A publicly reachable or always-on service must use a separately selected hosting environment with its own deployment adapter; the standard Termux process is not treated as a reliable production host. Deployment support begins as a dry-run manifest so that target, files, environment-variable names, and rollback metadata can be reviewed before any remote action.
